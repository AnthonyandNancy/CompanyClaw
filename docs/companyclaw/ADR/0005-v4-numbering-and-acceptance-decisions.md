# ADR 0005：V4.0 编号体系、四维验收口径与业务规则裁决

- 状态：已采纳
- 日期：2026-10-09
- 上游基线：`9e01612497c7f4e85bf9599a883042d550a38bad`（分支 `feat/companyclaw-foundation`）
- 依据：
  - 《CompanyClaw 修改实施书 4.0》§0–§22
  - 产品负责人正式裁决：4 项需求冲突 + 7 项待确认问题（2026-10-09）
  - 需求拆解阶段产出：业务规则 `BR-01`–`BR-42`
- 影响：所有 V4.0 实施文档、功能追踪矩阵、测试报告与验收结论的编号和口径

## 1. 背景

V4.0 要求把最初确认的通用产品功能补齐到生产调用链，并以 `F01–F14` 计算功能完成率。执行前暴露出两类障碍：

1. **编号双关**：功能编号 `F01–F14` 与工程阶段编号 `F00–F13` 同字不同义；安全风险等级 `R0–R3` 与 V2.0 工程阶段 `R0–R11` 同字不同义。二者都会污染追踪矩阵与完成率口径。
2. **验收口径不一**：功能实现、安装发行、外部平台真实可用、企业真实业务效果四项混用同一套状态字段，导致"没有企业账号就无法推进"和"模拟通过即等同业务通过"两种偏差都出现过。

本 ADR 固化裁决结果，不改变产品目标，不要求重新设计或推倒现有架构。

## 2. 决策一：编号体系分离

| 用途 | 统一编号 | 历史编号 | 说明 |
|---|---|---|---|
| 产品功能 | `F01`–`F14` | 4.0 §1.3 | 唯一功能完成率分母 |
| V4 工程实施阶段 | `PH00`–`PH13` | 4.0 §3 的 `F00`–`F13` | 只记录开发进度，进入不了完成率分母 |
| 安全风险等级 | `SEC-R0`–`SEC-R3` | V1/V4 的 `R0`–`R3` | 语义不变，仅加前缀 |
| V2.0 工程实施阶段 | `V2-R00`–`V2-R11` | V2 的 `R0`–`R11` | 仅作历史引用 |
| 业务规则 | `BR-01`–`BR-42` | 需求拆解阶段的 `R1`–`R42` | 顺序一一对应 |

### 2.3 使用纪律

1. 新建文档、追踪矩阵、测试报告中禁止出现含义不明的裸 `R2`；必须写 `SEC-R2` 或 `V2-R02`。
2. 工程阶段只写 `PHxx`；禁止在功能上下文里使用 `F00`–`F13` 表示阶段。
3. 历史文件、Git Commit、原始文档引用不做破坏性重命名，通过本 ADR 的映射表兼容。

## 3. 决策二：四个独立验收维度

| 维度 | 名称 | 责任人 | 判定依据 | 产出标志 |
|---|---|---|---|---|
| A | 通用功能实现验收 | DS（实现者） | 真实代码 + 生产调用链 + 真实执行器 + 通用正/负向测试通过 + 无关键 Mock 或不可达实现 | 决定 `IMPLEMENTED/14` |
| B | 安装与发行验收 | DS 提供可复现构建与安装验证 | 自包含 EXE、依赖装配、首次启动、升级、卸载、配置保留 | `INSTALLER_READY` |
| C | 外部平台真实验收 | DS 提供适配代码与测试程序；有账号者执行 | 真实微信扫码/收发/文件、真实 DeepSeek 等模型 API、外部网络与接口兼容 | 无账号时标 `UNVERIFIED` |
| D | 企业真实业务 UAT | 产品负责人 | 实际物业/ERP/财务系统的使用效果 | `ENTERPRISE_UAT_APPROVED` |

规则：

1. 四维分别记录状态，字段独立，禁止互相冒充或合并计算。
2. 维度 D 不是维度 A 的前置条件；缺少企业账号不得停止通用功能开发。
3. 维度 A 通过也不得表述为企业业务已验收。
4. 维度 C 缺少真实账号时，只允许把**实际平台验证**标为 `UNVERIFIED`，不允许因此省略功能实现。

## 4. 决策三：完成率与打包存在性

### 4.1 F01–F14 判为 `IMPLEMENTED` 的条件

1. 真实功能代码存在。
2. 生产调用链完整（正式用户入口可达）。
3. 真实执行器接通。
4. 通用功能测试通过。
5. 安全负向测试通过。
6. 不存在关键 Mock、占位实现或不可达实现。

已开发但尚未连通生产执行器的代码，不得计入已实现。

### 4.2 打包存在性的归属

- 对 `F01–F11`、`F13`、`F14`：是否已打入最终 EXE 属**维度 B（安装与发行验收）**指标，不直接影响其源码功能实现状态。
- `F12`（自包含安装与升级）本身即安装能力：必须完成真实安装包构建与相应安装验证，才能判 `IMPLEMENTED`。
- 所有必要运行组件必须在最终安装包中存在且可启动，否则 `INSTALLER_READY` 不得置为通过。

### 4.3 完成率公式

```
功能实现完成率 = IMPLEMENTED 功能数量 / 14
```

不得把未连通生产执行器的代码统计为已实现；不得使用无代码证据的百分比。

## 5. 决策四：7 项业务规则裁决

以下条款作为 V4.0 补充规则优先适用，并与 `BR` 条目合并使用。

### 5.1 未知业务站点的写入边界（补充/收窄 BR-10、BR-11）

1. AI 可在已授权目标内进行经安全判定的读取与探索（`SEC-R0`/`SEC-R1` 范围）。
2. 不得仅凭"查询""搜索""下一步"等按钮或菜单名称认定操作无副作用。
3. 对无法可靠识别写入事务边界的网页或 Windows 软件，不允许远程自动保存或提交。
4. 可以提供本机监督执行方式，但必须由本机操作者明确授权。
5. 对具备可信事务边界的系统，可使用经验证的受控执行路径完成远程写入。
6. 员工已在微信同意修改，也不能绕过执行层的写入约束。
7. 不允许 Agent 自行扩大工具权限；不允许把通用鼠标点击当作可靠的业务写入拦截机制。
8. Browser 与 Windows 的通用读取、导航、控件操作与受控写入接口必须全部实现；不得因未知业务系统不允许自动保存而省略这些操作能力。
9. "通用功能完成"与"任意企业系统都能自动安全写入"是两个不同概念，验收与对外表述均须区分。

### 5.2 无真实微信身份时的 F03/F10 判定（细化 BR-35）

`F03` 微信通道必须实现：真实插件接入与初始化；扫码、绑定、解绑与重连；可信消息来源识别；微信消息进入任务编排；进度与审批消息返回；消息去重与异常处理。

`F10` 文件回传必须实现：文件产物管理；文件完整性与类型校验；收件身份检查；发送权限与敏感性校验；调用真实微信插件文件发送接口；发送失败、重试与送达状态处理。

允许通过受控的微信平台边界模拟完成通用集成测试，但必须使用正式生产入口、真实业务适配代码与真实文件处理链路；不得只测试 Mock 消息函数，也不得预先编造发送成功结果。

满足以上条件后，可标 `IMPLEMENTED`，同时将真实微信平台验收标为 `UNVERIFIED`；不得对外宣称微信真机已测试通过。

### 5.3 无线上模型 API Key 时的 F02 判定（细化 BR-35）

必须完整实现：DeepSeek 等模型配置；自定义 Base URL、Model ID、API Key；凭据安全保存；模型连接测试；工具调用能力检测；工具执行结果回填；模型切换实际生效；错误处理与中文提示；模型能力不足时正确降级或拒绝不支持的任务。

使用符合真实协议的可控测试模型服务验证多轮工具调用与结果回填，不得只模拟普通聊天成功。

完成后 `F02` 可标 `IMPLEMENTED`，真实 DeepSeek 平台兼容性单独记录验证状态；员工日后自行提供 API Key 即可，不得要求员工手工修改 OpenClaw JSON、执行 npm 或配置开发环境。

### 5.4 群聊允许范围（收窄 BR-15）

V4.0 仅允许微信私聊触发电脑控制。群聊禁止：创建电脑操作任务；查看个人任务详情与进度；审批业务修改；暂停、恢复、取消其他任务；读取文件或产物；获取本机设备及授权信息。

若微信插件支持普通群聊文本消息，可按原生聊天策略处理非敏感内容，但不得暴露个人设备信息，也不得执行任何远程电脑操作。

V4.0 不开发群聊权限开放开关；将来如有需求另行评估。

### 5.5 敏感文件判定归属（细化 BR-25、BR-27）

1. 跨用户文件：直接禁止访问或发送，普通审批不能解除。
2. 非授权文件目录：直接拒绝任意读取与发送；如需导入必须走单独的受控授权流程。
3. 企业保密文件、个人信息与受限业务数据：默认要求审批，并受企业 IT 策略约束。
4. 来源或敏感性无法确认的文件：按敏感文件处理。
5. 普通授权任务产生的非敏感报表：可按已批准的任务级授权规则发送。
6. 文件发送对象仅限可信绑定的本人微信身份；未来若增加额外收件人审批机制再另行定义。

敏感性判定由独立安全策略层负责，Agent 不具有最终裁决权；判定不得只依靠文件扩展名、文件名或模型自述；不确定时取保守策略。

同一任务内已批准且明确涵盖收件人、文件范围、用途与敏感级别的发送动作，不重复审批；超出原授权范围必须重新确认。

默认规则由产品实施层提供；企业 IT 后续可增加更严格的分类策略，模型不得自行放宽。

### 5.6 取消或急停后已提交业务的处置（细化 BR-24）

1. 取消或急停后立即停止后续工具派发。
2. 已经发生的业务写入不得自动视为撤销。
3. 在安全且仍获授权的情况下，允许执行只读回查以确定是否提交成功。
4. 回查成功后记录实际状态。
5. 无法确认时标记为 `PARTIAL` 或现有等价的"待核验"状态，并记录不确定原因。
6. 不得因响应超时而重新点击保存或提交。
7. 不允许自动执行逆向修改、回滚或再次提交。
8. 任务中心与微信应提示员工当前状态及需要确认的内容。

如需恢复或修正业务数据，必须由员工重新下达操作指令，按新的任务与审批流程执行。

优先复用现有任务状态机，不为同一语义重复增加状态。

### 5.7 远程授权默认有效期与撤销粒度（细化 BR-16）

首次远程电脑控制必须由本机员工明确开启授权；默认有效期 **7 天**（本机远程操作授权的有效期，不是微信扫码绑定关系的有效期）。

1. 提供 1 天 / 7 天 / 30 天的配置选项。
2. 企业 IT 可设置更严格的最大有效期。
3. 授权到期后不允许自动无限续期。
4. 续期必须通过本机可信交互重新确认。
5. 员工可随时撤销全部远程授权。
6. 员工可取消指定任务或拒绝指定操作。
7. 已签发但未使用的高权限审批，在相关授权撤销后立即失效。
8. 已派发且不可中断的操作必须按真实状态处理，不得假装撤销成功。
9. 应用应明确显示授权剩余时间、有效范围与关闭入口。

撤销粒度分三层：

- **全局授权**：关闭整个设备的微信远程电脑控制。
- **任务级授权**：取消某个任务及其尚未派发的操作。
- **动作级授权**：拒绝或撤销尚未消费的 `SEC-R2` 审批票据。

远程操作授权整合进微信绑定后的首次使用引导，以明确易懂的方式获取本人同意，不增加 npm、MCP 或其他技术性配置；首次使用的主要配置仍只有"模型"和"微信扫码"两项。

## 6. 决策五：两项偏差纠正

### 6.1 企业业务 UAT 不得影响通用功能完成率

DS 必须实现：OpenClaw Agent 自主规划；真正可执行的 Browser 工具；真正可执行的 Windows UIA / Broker；Web 与 Windows 混合任务；微信消息进入任务系统；微信审批与任务恢复；文件处理与回传；自包含安装与自动启动。

通用功能验证允许在自建 Web 页面、自建 Windows 测试程序与受控平台模拟环境中完成。

- 不得以缺少公司物业/ERP/财务系统账号为由停止上述功能开发。
- 不得将模拟环境中的成功表述为公司实际业务系统已通过验收。
- 功能实现、平台兼容性、企业业务适配三者分别记录。

### 6.2 不得为了安全把 OpenClaw 变成固定脚本机器人

必须保留 OpenClaw 原生：自然语言任务理解；多轮上下文；自主规划；动态工具选择；页面与窗口状态观察；多步骤任务执行；错误恢复；Skills、Plugins 与可扩展工具架构。

安全策略只负责约束实际执行权限，不削弱模型的理解、规划与推理能力；允许采用安全执行适配器、目标授权与业务提交审批，不允许把所有操作改成预先写死的菜单脚本。

本地原生模式与微信远程模式必须区分可信来源，不得因增加远程安全策略而导致本地正常能力无故退化。

## 7. 后果

1. 本 ADR 生效后，V4.0 新文档、追踪矩阵、测试报告一律使用 `F` / `PH` / `SEC-R` / `BR` 编号体系。
2. 历史文件与 Commit 不做破坏性重命名；引用历史编号时附带映射。
3. 需求拆解阶段的 4 项冲突与 7 项待确认问题全部关闭，不再重复询问。
4. 后续主流程：PH00 源码核查 → 缺口分析 → Implementation Plan → 真实代码修改 → 通用功能测试 → 安装包交付 → 四项独立结论。
5. 仅当出现需要业务负责人批准的新业务范围、企业生产权限或外部授权时，才提出新的决策问题。

## 8. 不改变

- 产品目标：员工安装 EXE、配置本人模型、扫码绑定微信，通过微信自然语言让 Agent 在授权范围内操作浏览器、Windows 软件与 Office 文件，必要时完成微信审批与结果回传。
- `SEC-R0`–`SEC-R3` 的风险语义与"远程不得绕过受控桥接"的硬边界。
- 已有 Broker、策略层、任务状态机、微信插件桥接、资源打包等有效实现继续复用，不重复开发。
- 历史验收编号 E01–E20、PKG-01–10 与既有 ADR 保留有效。
